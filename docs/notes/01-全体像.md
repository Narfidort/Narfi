# 1. 全体像：何を信じれば、検査結果を信じてよいか

## 1.1 v1 の問題

v1 の検査器（`v1.0` タグの `src/check.rs`）は、証明の各行を読みながら「この行は推論規則に合っているか」を
その場で判断していた。判断のためのコードには、次のようなものが全部まざっていた。

- 単一化（`h(a, b)` の暗黙の引数を推測する）
- `let` や `def` の展開
- 自動証明（`ring`・`linarith`）
- 推論規則そのもの

このどこかにバグがあれば、間違った定理が通るかもしれない。「Narfi の結果を信じてください」と
言うには、1300 行の `check.rs` と 400 行の `arith.rs` の **全部** が正しいと信じてもらう必要があった。

## 1.2 v2 の考え方：作る人と確かめる人を分ける

```
elab（推敲器）  ── 証明項 ──►  kernel（核）
「どうやって証明するか」を探す      「その証明が規則どおりか」を確かめるだけ
推測・探索・展開をしてよい          推測しない。書かれたとおりに1段ずつ確かめる
信じなくてよい                       これだけを信じる
```

これを **de Bruijn 基準** と呼ぶ（N. G. de Bruijn が 1960 年代の Automath で示した考え方）。
Lean・Coq・Isabelle・HOL Light もこの形をしている。

ポイントは **確かめるのは、見つけるより易しい** こと。

- `linarith` で言えば、「どの仮定を何倍して足せば矛盾が出るか」を探すのは大変（Fourier–Motzkin の消去法）。
  しかし係数を渡されれば、掛けて足して定数になるかを見るだけで済む（第5章）。
- `h(a, b)` で言えば、`h` の ∀ に何を代入すればよいかを推測するのは単一化の仕事。
  しかし代入する項が書かれていれば、代入して形を比べるだけで済む。

## 1.3 証明項

elab が kernel に渡すのは **証明項**（`src/kernel/proof.rs` の `Proof`）。
証明を「どの推論規則を、どの前提に、どの順で使ったか」の木として書き下したもの。

たとえば次の証明は

```narfi
thm or_elim :
  h : P ∨ Q, hpr : P → R, hqr : Q → R
  ⊢ R

cases h
  Case left h₁
    hpr(h₁)
  Case right h₂
    hqr(h₂)
```

次の証明項になる（読みやすく書き直したもの）。

```
OrE( Hyp(h),
     h₁. ImpE(Hyp(hpr), Hyp(h₁)),
     h₂. ImpE(Hyp(hqr), Hyp(h₂)) )
```

「∨除去を h に使い、左の場合は →除去を hpr と h₁ に使い、右の場合は…」と読める。
kernel（`src/kernel/check.rs` の `infer`）は、この木を根から順に検算する。

## 1.4 実際に kernel が止めた例

v2 を作っている途中で、kernel の誤りではなく、kernel と elab の **食い違い** が見つかった。

`conv.add` を補題として使う `conv.add3` で、elab は証明を作れたのに、kernel が
「→除去の前提：示されているのは「c ⟶ γ」だが、必要なのは「e ⟶ γ」」と拒否した。

原因は、定理の関数記号のパラメータ `a, b, c` を `d, c, e` に付け替える処理
（`src/syntax.rs` の `instantiate`）が、1つずつ順に置き換えていたことだった。
`a→d`、`b→c` のあとで `c→e` を行うと、2番目で `b` から変わった `c` まで `e` になってしまう。
**同時代入**（すべてを一度に置き換える）にしなければならない。

この例は2つのことを教えてくれる。

1. elab と kernel が別々に計算するので、どちらかの誤りが **食い違い** として表に出る。
2. このバグは「正しい証明が通らない」方向だった。記号をまとめて同じものに付け替えても、
   図式（どんな解釈でも成り立つ定理）の正しい具体化なので、**誤った定理を通す** ことはない。
   健全性（誤ったものを通さない）と完全性（正しいものは通す）を分けて考える習慣が大事。

## 1.5 それでも信じる必要があるもの（信頼の土台）

kernel だけを信じればよい、というのは正確には言いすぎで、次のものも信じる必要がある。

| もの | なぜ |
|---|---|
| `src/kernel/` | 推論規則の検算そのもの |
| `src/syntax.rs` の代入・自由変数 | kernel が使う（`subst`・`subst_many`・`free_vars`・`instantiate`・`rename_fn`） |
| 定理の **文** を正しく読んだこと | kernel が保証するのは「表示された文が証明された」ことまで。parser が文を読み違えたら、別の文が証明される。最後は人が文を読んで確かめる |
| 公理 | `axiom` で置いたものは証明されない。kernel は依存した公理を報告するだけ |
| Rust のコンパイラ・計算機 | どの証明支援系でも同じ |

`notation` も注意が要る。記法は表示を変えるだけで中身は変えないが、紛らわしい記法を定義すれば
人が文を読み違える。この危険は Lean などでも同じで、記法の定義も人が確かめる対象になる。

| ファイル | 役割 | 信じる？ |

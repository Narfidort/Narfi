# 8. 型の定義と商：ℝ を作る（v2.2）

## 8.1 目標

あなたの最初の目標はこうだった：

```
{a_n} ~ {b_n}  :⟺  ∀ε>0. ∃n₀. ∀n≥n₀. |a_n − b_n| < ε
C = { {a_n} ∈ ℚ^ℕ ; コーシー列 }
ℝ = C / ~
```

v2.2 で、これを **型として** 作った（`lib/reals/`）。ℚ は kernel の算術に組み込まれた順序体を使う
（ℚ 自体をペアノから作るのは同じ方法でできるが、まだやっていない）。

## 8.2 部分集合を型にする：typedef

`C`（コーシー列全体）は `ℕ → ℚ` の部分集合だが、HOL では「型」と「集合」は別物で、
`∀a:C. …` と書くには C が型でなければならない。そこで **typedef**：

```narfi
typedef CauSeq := {a : ℕ → ℚ | cauchy(a)}
  choose (n:ℕ ↦ 0)
  cauchy.const(0)
```

これで新しい型 `CauSeq` と、2つの定数ができる：

```
CauSeq.abs : (ℕ → ℚ) → CauSeq      元の世界から新しい型へ
CauSeq.rep : CauSeq → (ℕ → ℚ)      新しい型から元の世界へ
```

そして「CauSeq と {a | cauchy(a)} は1対1」を表す3つの公理：

| 公理 | 意味 |
|---|---|
| `rep_prop` | rep で取り出したものはコーシー列 |
| `abs_rep` | 取り出して戻すと元どおり |
| `rep_abs` | コーシー列なら、戻して取り出すと元どおり |

### なぜ「空でない」証明が要るか

HOL では **どの型も空でない**（選択の `some` で必ず元が作れる）。もし空の集合で typedef できたら、
`rep_prop` から「空の集合の元がある」が出て矛盾する。だから typedef には、集合が空でない証明
（ここでは定数列 0 がコーシー列であること）を要求する。`sorry` で済ませると、その型を使う定理は
すべて「未完成」になる（`tests/unsound_typedef.narfi` で実際に ⊥ を出して確かめている）。

### 保存的であること

typedef は新しい公理を足しているように見えるが、**保存的** である：新しい型 T を
「{x | φ} そのもの」、abs を「φ を満たせばそのまま、満たさなければ適当な元」、rep を「包含写像」と
読めば、3つの公理はすべて成り立つ。だから typedef で矛盾が増えることはない（空でなければ）。

## 8.3 商を作る：同値類の集合

商 `C/~` は「同値類全体」。同値類は集合（述語）なので、HOL では次のように作れる：

```narfi
typedef RealC := {c : CauSeq → Prop | ∃a:CauSeq. c = {b : CauSeq | a ~ b}}
def cls(a : CauSeq) : RealC := RealC.abs({b : CauSeq | a ~ b})
```

「`CauSeq → Prop` の値（集合）のうち、ある a の同値類になっているもの」を型にした。
`cls(a)` が a の同値類 [a]。

Lean や Coq は商を kernel の特別な規則（商型 `Quot`）として持つが、HOL では **新しい規則なしに**
typedef と集合だけで作れる。最初に「商型が必要らしい」と聞いた件の答えはこれで、
HOL の立場では商型は要らない（集合と型の定義があれば十分）。

## 8.4 商の3つの性質

商がちゃんと「同値なものを同一視したもの」になっていることは、次の3つで言える
（`lib/reals/real.narfi`）。

| 名前 | 内容 | 証明の要点 |
|---|---|---|
| `cls.sound` | a ~ b なら [a] = [b] | 同値類が集合として等しい（`setext`）ので、abs をかけても等しい |
| `cls.exact` | [a] = [b] なら a ~ b | `rep_abs` で同値類を取り出し、a ∈ [a] = [b] から b ~ a |
| `cls.surj` | どの実数も、ある列の同値類 | `rep_prop` で取り出した同値類の代表 a をとる |

`sound` と `exact` で「[a] = [b] ⟺ a ~ b」、`surj` で「すべての実数は [a] の形」。
この3つがあれば、以後は `RealC` の中身（集合の集合）を見ずに、代表元 a で議論できる。

`exact` には、~ が **同値関係**（反射律・対称律・推移律）であることが本質的に要る。
対称律では |x − y| = |y − x|、推移律では三角不等式と ε/2 の議論を使った。

## 8.5 v2.2 で見つけて直した、kernel のバグ

この章の `cls.exact` を書いていて、kernel の健全性のバグが見つかった。

同時代入 φ[x₁ := t₁, x₂ := t₂] は、いったん x₁, x₂ を仮の名前 `%0`, `%1` に置き換えてから t₁, t₂ を入れる。
ところが代入の途中で束縛変数の付け替えが起きると、内側でもう一度同時代入をして、同じ `%0` を使っていた。
その結果、

```
def k(a : ℕ) : ℕ := some({b : ℕ | b > a})
```

に `a := b` を入れたものが、正しい `some({b' | b' > b})` ではなく `some({b' | b' > b'})` になった。
kernel の定義の展開もこの代入を使うので、kernel は「k(b) = some({y | y > y})」を反射律で受け入れ、
選択公理と合わせて **⊥ が証明できた**（`tests/regress/subst_placeholder.narfi`）。

修正は、仮の名前を毎回新しくすること。v2.1.1 として main に出した。

教訓：

1. **kernel も間違える**。「kernel は小さいから正しい」ではなく、「小さいから読んで確かめられる」。
   今回も、elab と kernel の食い違い（elab が通せない証明があった）から原因に辿り着いた。
2. 健全性のバグは、**それを突いて ⊥ を出すテスト** として残す。修正前のコードでテストが失敗することも
   確かめた（テストがバグを捕まえられることの確認）。
3. 代入・束縛変数の扱いは、証明支援系の古典的なバグの源。de Bruijn 添字（変数を名前でなく
   番号で表す方法）を使えば、この種のバグはそもそも起きにくい。kernel を作り直すなら検討に値する。

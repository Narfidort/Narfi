# Narfi の設計原則

**Narfi** = **N**atural **A**nnotated **R**easoning **F**orward **I**nteractive（「ナーフィ」）。
名前は作者のユーザー名 Narfidort から。

新しい書き方・機能を足すとき、迷ったら、この文書に照らして決める。原則どうしがぶつかるときは、番号の小さいものを優先する。
この文書を変えるときは、理由を添えて変える（変えた版を下の「改訂」に書く）。

## コンセプト

1. **手書きの証明と対応する**：紙の証明を書く順に、紙の証明と同じ粒度で書ける。書いたものは、そのまま証明の文章として読める。
2. **量化子を剥がす気持ちよさ**：∀ を `Fix` で剥がし、∃ を `Obtain` で取り出し、→ を `assume` で開く。証明は「goal の形を見て、1 つずつ剥がしていく」作業として進む。
3. **前向きで、天下りでない**：なるべく自然演繹の前向きの推論（分かっていることから、分かることを増やす）で完結させる。「なぜかこれを示せば十分」という天下りの書き方に頼らない。
4. **読める形式証明**：Lean のような信頼できる検査器を持ちながら、数学の答案として読める証明言語の位置を目指す。
5. **安全な設計**：Rust のように、間違いはできるだけ早く・はっきり止め、直し方を示す。

## 原則

### 1. 信じる部分は小さく
正しさを判断するのは kernel（`narfi/src/kernel/`）だけ。推敲器（elab）・パーサ・エディタにバグがあっても、誤った定理は通らない。

- 新しい機能は、今ある kernel の規則に落とせるものに限る。
- kernel を変えるときは、理由を仕様（[language/logic.md](language/logic.md)）に書き、「誤りを通さない」テストを付ける。
- 自動証明（ring・linarith・decide）は証明書を出し、kernel が検算する。

### 2. 勝手に補わない
推論・探索で分かったことも、ソースに書かれるまでは証明に使わない。

- 分かったことは「直し方」として示し、Tab などの明示的な操作で入れる（Rust のエラーと help）。
- 例：仮定の中身（`Fix ε | hε : ε > 0`）、事実の行の根拠（`φ by linarith`）は省略できず、省略するとエラーと候補が出る。
- 型・ソートの推論など、読む人にとって情報のないものは補ってよい（何を補ったかは表示で確かめられる）。

### 3. ソースが読むものそのもの
証明に使ったものは、すべてソースに見えている。

- 表示を変えるもの（日本語シュガー、∴ の表示、添字・積の見え方）は、ファイルを変えない。
- ファイルは純粋な ASCII で書け、キーボードだけで打てる（Unicode の記号でも書ける）。

### 4. 書き方は 1 つ
同じことの書き方は 1 つにする。

- 例外は、自然演繹の規則の名前（`and.intro` など。授業で規則を明示するため）だけ。
- 古い書き方は、警告と自動の書き換えを付けてから消す（原則 8）。

### 5. 名前を導入するのは 6 つの文だけ
`Fix`・`assume`・`Obtain`・`cases`・`induction`・`by_contra`。それ以外の行は、事実の行（`h : φ by j`）か、根拠だけの行か、`choose`・`let`・連鎖。
これが「量化子を剥がす」操作とちょうど対応する。

### 6. 記法は教科書に合わせ、曖昧にしない
数学の慣習（添字 `a_n`、数のあとの積 `2x`、Σ）に従う。ただし読み方が 2 通りになるもの（`ab` を積と読むなど）は入れない。

- 名前は `.` で階層を作る（`abs.triangle`、`sum.succ`、`mat2.e00`）。定理名は「対象.性質」の順にする。

### 7. 言語の核は自然言語に依存しない
予約語・記号・ファイルの書式は、特定の自然言語に依存させない。

- 予約語は ASCII の英語。全角文字を構文に使わない。
- 日本語での読み（Prose・日本語シュガー）は「表示の層」で、言語の核と分ける。ほかの言語の読みも同じ仕組みで足せるようにする。

### 8. 失敗は局所的に、変更は移行つきで
- 1 つの宣言の失敗が、ほかの宣言の検査や表示を止めない。
- 書き方を壊す変更は、移行（警告＋自動の書き換え）とバージョンを上げることをセットにする。

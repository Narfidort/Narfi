# 6. まだ足りないもの

（v2.0 の時点で書いたもの。6.1・6.2 は v2.1 で実装した。第7章を参照）

v2.0 で「何を信じればよいか」はだいぶ小さくなった。ここでは、まだ足りないものと、
それが数学的・設計的にどういう問題かを書いておく。

## 6.1 λ 抽象と関数型（v2.1）

`(a + b) ⟶ (α + β)` のように「数列の和」を書くには、`n ↦ a(n) + b(n)` という **関数そのもの** を
値として作る必要がある。これが λ 抽象 `λn. a(n) + b(n)`。

λ を入れると、論理は一階から **単純型理論**（Church の HOL）になる。

- 型に `σ → τ` が加わり、関数が値になる（`∀a:ℕ → ℝ. …` と書ける）
- 定義的等しさに **β 簡約** `(λn. t)(s) ≡ t[n := s]` が加わる
- 集合は「述語」として扱える（`{x : ℕ | φ(x)}` は `λx. φ(x) : ℕ → Prop`）
- 商（`C/~`）も述語の集合として作れる（Isabelle/HOL・HOL Light はこの方法）

コーシー列の商で ℝ を作る（あなたの目標）には、このどれもが要る。v2.0 の多ソート一階述語論理は
単純型理論の一部分なので、v2.1 は「型に → を足す」拡張として自然に入れられるはず。

## 6.2 二階の図式の具体化

`or_elim` の `P`・`Q`・`R` は「どんな命題でもよい」はずだが、v2.0 では **同じ名前の述語でしか** 使えない。
`P` に `x > 0` のような論理式を入れるには、述語変数への代入（二階の図式の具体化）が要る。
これも λ（`P := λx. x > 0`）があれば素直に書ける。

## 6.3 健全性の証明

「kernel が通した定理は、本当に正しい」ことを **証明** したわけではない。v2.0 でやったのは：

- 仕様書（`docs/v2/spec.md`）で規則を明文化した
- 規則ごとに「間違った証明項を拒否する」テストを書いた（`src/kernel/tests.rs`）

本当に保証するには、各規則が「正しい命題から正しい命題しか導かない」ことを示す（**健全性定理**）。
数学的には、各規則についてモデル（解釈）で真であることを確かめる帰納法。これを紙に書くのが次の段階で、
さらに進めば kernel 自体を別の証明支援系で検証する（HOL Light の kernel を CakeML で検証した Candle のような研究がある）。

## 6.4 外部の検査器での再検査（v2.2）

証明項を Lean 4 や Isabelle の形式に書き出して、そちらでも検査する。Narfi の kernel にバグがあっても、
独立した検査器が通さなければ分かる。「Narfi を信じてください」と言わずに済む、最も強い方法。

## 6.5 公理を減らす

`lib/analysis/real.narfi` の三角不等式・`max` の性質は公理のまま。順序体の公理と `abs`・`max` の定義から
証明すれば、公理の一覧が「標準的な数学の公理」だけになる。専門家が見るのはこの一覧。

## 6.6 elab の不完全さ

elab は正しい証明でも通せないことがある（健全性ではなく完全性の問題）。たとえば：

- `linarith` は非線形な事実（`x² ≥ 0`）を知らない
- 多相な補題の型が、使い方によっては決まらないことがある
- 関数記号を持つ定理の具体化は、単一化で決まる場合だけ

これらは kernel を変えずに elab を改良すれば直せる。kernel を小さく保ち、便利さは elab で
増やす、というのが de Bruijn 基準の利点。
